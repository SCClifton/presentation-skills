# Assembly and rendering

## Preserve the chosen medium

Use the user's requested presentation format and existing template. When a presentation authoring tool or specialist file workflow is available, use it for native objects, export, and rendering. This skill does not require a named library, paid connector, or model provider.

Inspect an existing file before modifying it. Identify dimensions, masters, layouts, notes, charts, links, comments, and user edits that matter to the request. Preserve the original and make reversible working changes unless the user requests otherwise.

## Translate the slide plan into a visual system

Choose a small set of shared decisions before assembling a new deck:

- The content frame, margins, grid, and column relationships.
- Heading, body, annotation, and source hierarchy.
- Section navigation and page numbering where needed.
- How categories, emphasis, observations, and proposals are distinguished.
- How sources and detailed evidence are located.

Use an approved template for these decisions when supplied. Avoid adding a second visual system on top of it. A change in organisation should change the appropriate brand layer without requiring a rewrite of the general method.

Establish one representative content slide, one evidence slide, and any unusual layout early. Inspect them at the intended viewing size before replicating them. Do not discover a broken table style after applying it to the whole deck.

## Arrange objects by reading order

Give the slide a dominant entry point. Make the next reading step visually plausible through alignment, proximity, and hierarchy. Align related objects and use consistent spacing. Avoid disconnected boxes that require the reader to guess their order.

For two-column layouts, allocate width according to need. A chart with long labels may need most of the slide. A mechanism with a short explanation may need a wide diagram and narrow text column. Equal columns are an option, not a rule.

Allow empty space when it helps the main point register. Avoid decorating a clear explanatory slide solely to make it look busy. Conversely, do not place a complicated table in a small corner just to preserve whitespace.

## Manage density

Treat readability at the final size as the acceptance test. A universal word limit is unreliable because headings, diagrams, tables, and speaker settings impose different demands.

When a slide feels crowded:

1. Remove repetition and text already evident in the visual.
2. Shorten or restructure the explanation without losing the qualifier.
3. Enlarge or simplify the main evidence object.
4. Split distinct reasoning jobs into separate slides.
5. Move optional detail to notes or an appendix when the delivery setting permits.

Reducing text size is a late adjustment, not the primary compression method. Do not hide material conditions in illegible footnotes.

## Keep the information usable

Prefer native text, shapes, tables, and charts when the recipient needs to edit them. Use images for photographs or source illustrations when appropriate. A visually accurate chart image is not an editable chart; disclose that distinction when it matters.

Check that exported data series, axis labels, chart categories, and diagram arrows agree with the intended claim. Maintain source links in notes or references if the format allows them. Use meaningful alt text for substantive visual objects when supported, and do not rely on colour alone to encode a decision or exception.

When the user requests an existing slide count or arrangement, preserve it unless they approve a change. If you must substitute a visual because a tool cannot reproduce it, make the tradeoff explicit.

## Render, inspect, repair

Render every final slide. Inspect both a deck overview and individual slides at useful resolution. The overview reveals repetition, pacing, inconsistent hierarchy, and an unbalanced mix of layouts. Individual views reveal clipping, tiny labels, ambiguous arrows, and text that collides with the footer.

After a repair, re-render the affected slides. If the repair changes shared theme or layout behaviour, recheck every affected slide.

Verify that the requested file exists and reopens or reimports when the environment permits. Check that the output contains the expected slides and editable objects. An export command completing is weaker evidence than opening and inspecting the saved result.

If a renderer or native-format check is unavailable, report exactly what was inspected and what remains unverified. Do not imply that browser rendering proves a native presentation will behave identically in every editor.
