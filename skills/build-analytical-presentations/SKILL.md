# Build analytical presentations

Build a presentation that helps its audience understand something consequential or make a supported decision. Make its reasoning visible through the sequence, writing, and arrangement of the slides.

This skill supplies presentation judgement. Use the available presentation tools for the requested file format. Follow a supplied company template and task-specific terminology; do not invent a house brand or require a particular software stack.

## Start from the assignment

Establish the following from the request and available material. Ask only about missing information that changes the work. For minor gaps, state a reasonable assumption and continue.

- Who will read or hear this, and what do they already know?
- What should they understand, decide, or do afterwards?
- Is this a live presentation, a document to read independently, or both?
- What duration, length, evidence, delivery format, and template constrain it?
- Which statements are verified, estimates, interpretations, or proposals?

Preserve a requested slide count, sequence, output format, and existing edits. When those choices constrain quality, explain the tradeoff and work within them. Do not turn an edit into an unsolicited rebuild.

Read [briefing and adaptation](references/briefing-and-adaptation.md) when selecting the presentation mode or adapting material to a different audience.

## Build the argument before the slides

Write a short internal brief: audience, outcome, central message, evidence limits, and the intended route through the material. Then develop a sequence in which each section earns the next.

- For teaching: establish the question, define the essential concepts, explain mechanisms, examine examples and limits, then synthesise.
- For decisions: put the recommendation and decision near the front, develop the evidence and alternatives, then return to the ask and its conditions.
- For technical reviews: state the requirement, explain the design or process, show results against acceptance criteria, and resolve risks or next tests.

These are starting patterns, not mandatory chapter lists. Use only the steps the audience needs. Short decks can make the reader promise in a subtitle instead of spending a slide on orientation.

Read [narrative construction](references/narrative.md) for section logic, transitions, pacing, and compression.

## Create a slide plan

For a new deck or substantial rewrite, create an internal slide plan with:

| Field | What it must resolve |
| --- | --- |
| Purpose | The question answered or the decision advanced |
| Headline | The claim, question, or useful topic label |
| Content | The minimum explanation, comparisons, or definitions needed |
| Evidence | The source, measure, calculation, or stated evidence gap |
| Layout | The arrangement that makes the relationship understandable |
| Handoff | Why the next slide follows |

The plan can be a table or equivalent working representation. Show it to the user when requested or when storyboarding is the deliverable. Otherwise continue into assembly without introducing an extra approval stop.

Each slide should have one dominant job. It may contain several related facts if they form a single explanation. If you cannot name the job without saying "and another thing", split or restructure it.

## Write slide copy

Make the wording precise enough to carry the reasoning and short enough to scan.

- Use a claim headline when the evidence supports a clear conclusion. Use a question when the slide investigates it. Use a topic label when introducing or navigating a section.
- Write in short connected paragraphs when explaining causality. Use bullets for parallel items or an actual sequence, rather than breaking every sentence into a bullet.
- Explain unfamiliar terms before relying on them. Keep technically necessary detail and remove decorative jargon.
- Emphasise the words or relationship the audience must notice. Do not highlight an entire page.
- Keep quantities attached to units, dates, baselines, and scope. Distinguish a measured result from a target or forecast.
- Use direct language, plain ASCII punctuation, and the requested language variant. Avoid invented slogans, vague labels, unsupported superlatives, and repeated closing catchphrases.

Read [writing and evidence](references/writing-and-evidence.md) for headline choices, numerical claims, caveats, and before-and-after examples.

## Select and assemble layouts

Choose an arrangement because it reveals a relationship, not because it fills space. Reuse a small, coherent layout vocabulary and vary it when the information changes.

Common arrangements include a section opener, a narrative explanation, text beside evidence, a dominant chart, a comparison, a mechanism diagram, a timeline, a structured table, and a synthesis or decision slide.

Read the relevant entries in [layout patterns](references/layout-patterns.md). Each entry describes when to use it, how to arrange it, what can vary, and how it fails. Do not apply every pattern to every deck.

Use [assembly and rendering](references/assembly-and-rendering.md) when creating or revising presentation files. Keep reading order, object alignment, source placement, spacing, and native editability coherent. Apply the current organisation's approved template without changing the reasoning merely to imitate a visual treatment.

When tools cannot create the requested file, deliver a clearly labelled storyboard and report the missing capability. Do not describe a storyboard, HTML preview, or unverified export as a finished PowerPoint.

## Review the complete presentation

Read the headlines in order, then read each section in full. Check that the ending resolves the opening promise and that the audience can distinguish evidence, inference, and the requested action.

For a presentation file, render and inspect every final slide. Repair overflow, cramped tables, unreadable labels, visual contradictions, and unintended object changes. Recheck any slide affected by a shared layout change.

Read [review and acceptance](references/review.md) before delivery. Include material evidence limits or unverified steps in the handoff. If the task stops at a storyboard, apply the narrative and evidence checks and state that rendering has not been tested.
